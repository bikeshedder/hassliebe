# Architecture

`hassliebe` is a data crate. It describes the JSON that Home Assistant expects on
its MQTT discovery topics, and nothing else. Anything that sends, receives or
interprets MQTT messages lives in other crates that depend on this one.

## Goals and non-goals

Goals:

- Faithful, typed coverage of the Home Assistant MQTT discovery schema.
- Usable for **writing** payloads (announcing devices) and **reading** them
  (bridges, debugging tools, tests).
- Works with any MQTT client and any async runtime, because it uses none.
- Small dependency footprint and fast compile times.

Non-goals:

- Publishing, subscribing, reconnecting, availability handling at runtime.
- Evaluating Jinja templates or validating semantic consistency
  (e.g. "unit matches device class"). That is the job of higher layers.
- Home Assistant REST/WebSocket APIs.

## Module layout

```
src/
  lib.rs            re-exports, crate docs
  string_enum.rs    macro for string enums with an Other(String) fallback
  common/
    availability.rs Availability, AvailabilityMode
    device.rs       Device (the "dev" block), connections, identifiers
    origin.rs       Origin (the "o" block)
    entity_category.rs
    qos.rs          Qos, serialized as the integers 0, 1, 2
    state_class.rs
    unit.rs         Unit of measurement
  component/
    mod.rs          Component enum (one variant per platform), Platform trait
    sensor.rs       Sensor, SensorDeviceClass
    binary_sensor.rs
    switch.rs
    number.rs
    select.rs
    button.rs
    text.rs
    light.rs        default ("basic") schema only for now
    cover.rs
  discovery.rs      DeviceDiscovery payload, topic helpers, HA status constants
  abbreviations.rs  expansion of abbreviated keys (feature "json")
```

## Key design decisions

### Plain structs with public fields

Structs have public fields and implement `Default`, so users can write
`Sensor { name: …, ..Default::default() }`. With the `builder` feature
(on by default), `derive_builder` additionally generates `SensorBuilder` etc.

Structs are deliberately **not** `#[non_exhaustive]`: that attribute forbids
struct-literal construction outside the crate, even with `..Default::default()`.
The price is that adding a field is a breaking change. While the crate is 0.x this
means a minor version bump, which is acceptable for a schema-mirroring crate.

### String enums with a fallback

Device classes, units and state classes change with Home Assistant releases. They
are generated by `string_enum!`, which produces a `#[non_exhaustive]` enum with an
`Other(String)` variant, `Display`/`FromStr`, and serde impls that map known strings
to variants and everything else to `Other`. This keeps deserialization of payloads
from newer Home Assistant versions working and lets users emit values the crate does
not know yet. This applies to closed sets such as `EntityCategory` too.

Variants may carry input-only aliases for legacy spellings Home Assistant still
accepts (e.g. the micro sign U+00B5 in `µg/m³`); serialization always emits the
canonical string. Each wire string maps to exactly one variant. Where Home
Assistant uses one string for different units (`"m"` for meters and months), the
variant is named after the string (`Unit::M`).

### Device classes per platform

Home Assistant uses **different** device class sets per platform. There is one enum
per platform (`SensorDeviceClass`, `BinarySensorDeviceClass`, `CoverDeviceClass`,
`NumberDeviceClass`, `SwitchDeviceClass`, `ButtonDeviceClass`, …), defined in the
platform's module. The single shared `DeviceClass` from `nrg-hass` is replaced.

### Components and the platform tag

Each platform struct implements a small trait:

```rust
pub trait Platform {
    /// "sensor", "binary_sensor", …
    const PLATFORM: &'static str;
}
```

`Component` is an enum over all platforms, serialized with an internal tag
`"platform"`. It is used inside device-based discovery (`cmps`), where every entry
must carry its platform. Two extra variants cover the rest of what may appear in
`cmps`:

- `Removed { platform }`: an entry with only the platform, which tells Home
  Assistant to remove that component.
- `Other { platform, config }` (feature `json`): platforms the crate does not model
  and lights with a non-basic `schema`, with the config kept as a
  `serde_json::Map`.

Deserializing `Component` and `DeviceDiscovery` needs these fallbacks, so it is only
available with the `json` feature. Serializing works without it.

### Two discovery styles

Home Assistant supports two ways to announce entities, and the crate supports both:

1. **Single-component discovery**: one retained message per entity on
   `<prefix>/<platform>/[<node_id>/]<object_id>/config`, payload is the platform
   struct itself (with its own `device` block).
2. **Device-based discovery**: one retained message per device on
   `<prefix>/device/[<node_id>/]<object_id>/config` (the docs define `<component>`
   as a platform or `device`), payload is `DeviceDiscovery` with the
   `device`, the `origin`, the `components` map (serialized as `cmps`) and optional
   shared options such as `availability`, `state_topic` or `qos`.

`discovery.rs` provides pure functions for both topics and the constants for Home
Assistant's birth/last-will topic (`homeassistant/status`, `online`/`offline`).

### Abbreviations: input only

Home Assistant accepts abbreviated keys (`stat_t`, `dev_cla`, `uniq_id`, `dev`,
`o`, `cmps`, `p`, …). The crate always **serializes full names**. For reading,
the `json` feature offers a function that expands abbreviations in a
`serde_json::Value` before deserializing, mirroring what Home Assistant does in
`mqtt/discovery.py`. The tables are ported from
`homeassistant/components/mqtt/abbreviations.py`. This keeps the structs free of
dozens of `#[serde(alias)]` attributes.

### Availability

Only the `availability` list (plus `availability_mode`) is modeled. The legacy
top-level `availability_topic`, `availability_template`, `payload_available` and
`payload_not_available` are not; when reading, they are ignored like any unknown
key.

### Docs over source

The Home Assistant MQTT docs decide. Where the core source differs (defaults,
required fields), types follow the docs and doc comments mention the source value.

### QoS

`Qos` serializes as the integers `0`, `1`, `2`, as Home Assistant expects. (The
`nrg-hass` version serialized variant names, which was a bug.)

## Scope for 0.1

Common: `Device`, `Origin`, `Availability`, `AvailabilityMode`, `EntityCategory`,
`StateClass`, `Unit`, `Qos`.

Platforms: `sensor`, `binary_sensor`, `switch`, `number`, `select`, `button`,
`text`, `light` (default schema), `cover`.

Discovery: single-component and device-based payloads, topic helpers, abbreviation
expansion.

Later, driven by real needs: `light` JSON/template schemas, `climate`, `fan`,
`lock`, `valve`, `water_heater`, `event`, `update`, `device_trigger`, `siren`,
`alarm_control_panel`, `vacuum`, `image`, `camera`, …

## Migration from nrg-hass

The initial code was copied from `nrg-hass`. Known changes needed:

- Remove everything that performs I/O: `announce()` in `discovery.rs`, `state.rs`
  (both use `rumqttc`), and the application config in `config.rs`.
- Delete the empty files `client.rs`, `mixins.rs`, `availability.rs` (top level).
- Fix the field name typo `availabilty` → `availability` in all components.
- Serialize `Qos` as integers.
- Split the shared `DeviceClass` into per-platform enums.
- Add `Deserialize` and `PartialEq` everywhere; replace `Arc<Device>` with `Device`.
- Replace the `Discovery` trait with `Platform`; `unique_id` is just a field.
- Convert enums to `string_enum!`, verify all values against current HA sources.

## Prior art

- `hass-mqtt-discovery` (Rust, unmaintained since 2022).
- `ha-mqtt-models-pydantic` (Python): typed models with abbreviation support and
  per-schema light parsing; a good reference for scope.
- `hqtt` (Go): SDK built around device-based discovery.
